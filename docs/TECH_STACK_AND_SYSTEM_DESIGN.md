# Tech Stack & System Design Documentation

## 1. Overview

The **NEFAC Chatbot** is a sophisticated **Agentic RAG (Retrieval-Augmented Generation)** system designed to perform deep research and answer questions using a hybrid of vector search, keyword search, and knowledge graph traversal. It employs a **Supervisor-Worker** agent architecture to orchestrate complex tasks, backed by a robust event-driven ingestion pipeline and a custom web crawler.

The system is built as a **Monorepo** containing:
1.  **Backend**: A stateful, asynchronous Python application using **LangGraph**.
2.  **Frontend**: A modern **Next.js 15** streaming chat interface.
3.  **Data Layer**: A suite of 5 specialized databases (Neo4j, Qdrant, Elasticsearch, Redis, Postgres).
4.  **Services**: Dedicated modules for **Crawling** (Web/YouTube) and **Ingestion** (Hybrid RAG).

## 3. System Architecture

The system follows a **Micro-Modular Monolith** architecture. While the code resides in a single repo, the components are logically distinct and communicate via defined interfaces or database state.

### 3.1 High-Level Data Flow
1.  **User Input**: Frontend sends message -> Next.js Proxy -> LangGraph API.
2.  **Agent Orchestration**: `DeepResearchGraph` receives input.
    *   **Supervisor** analyzes intent.
    *   **Workers** (Researchers) are spawned to execute tasks.
3.  **Retrieval**: Workers query the **Hybrid RAG Layer**.
    *   **Query Transformer** expands queries (HyDE, Multi-Query).
    *   **Retriever** fetches from Qdrant/Elastic/Neo4j.
4.  **Generation**: LLM synthesizes findings -> Streamed back to Frontend.
5.  **Persistence**: State is saved to Postgres after every step.

### 3.3 Database Interaction Model

The system uses a **Polyglot Persistence** strategy, where each database serves a specialized purpose. The backend interacts with these stores via specific libraries and abstraction layers.

#### 1. Knowledge Graph (Neo4j)
*   **Role**: Stores structured relationships (e.g., `Person WORKS_FOR Organization`). Used for **Graph RAG** to find multi-hop connections.
*   **Interaction**:
    *   **Write**: The Ingestion Service uses `DynamicLLMPathExtractor` to parse text into nodes/edges and writes via the Neo4j Python Driver.
    *   **Read**: The Backend uses `langchain-neo4j` to execute Cypher queries generated by the LLM (text-to-cypher) or predefined retrieval templates.

#### 2. Vector Store (Qdrant)
*   **Role**: Stores high-dimensional embeddings of document chunks. Used for **Semantic Search**.
*   **Interaction**:
    *   **Write**: Ingestion pipeline embeds text using OpenAI (`text-embedding-3-small`) and upserts vectors to Qdrant collections.
    *   **Read**: The Backend uses `langchain-qdrant` to perform cosine similarity searches, often retrieving the "Top K" most relevant chunks.

#### 3. Search Engine (Elasticsearch)
*   **Role**: Stores full-text indices. Used for **Keyword Search (BM25)** to find exact matches (names, case numbers) that vector search might miss.
*   **Interaction**:
    *   **Write**: Ingestion pipeline indexes raw text fields.
    *   **Read**: The Backend uses `langchain-elasticsearch` to execute BM25 queries. Results are often **Reciprocal Rank Fused (RRF)** with Qdrant results for Hybrid RAG.

#### 4. State Store (PostgreSQL)
*   **Role**: The "Brain" memory. Stores the persistent state of every agent interaction (threads, messages, current step).
*   **Interaction**:
    *   **Library**: `langgraph-checkpoint-postgres`.
    *   **Flow**: After every node execution in the graph, LangGraph automatically serializes the state (pickled) and writes it to the `checkpoints` table. This allows the system to pause, resume, or recover from failures seamlessly.

#### 5. Task Queue & Cache (Redis)
*   **Role**: Manages async background tasks and provides a fast cache for frequent operations.
*   **Interaction**:
    *   **Queue**: Used by the Ingestion pipeline to track job status.
    *   **Cache**: Can be used to cache LLM responses or expensive query results to reduce latency and cost.

## 4. Service-Level Details

### 4.1 Backend (`backend/src/`)
*   **Entry Point**: `app/server.py` defines the `deep_researcher` graph.
*   **Core Agents** (`core/agents/`):
    *   `supervisor/`: Orchestrates the research loop.
    *   `research/`: Executes tool calls and summarizes findings.
    *   `quick_agent/`: Fast path for simple queries.
*   **Graph Logic**:
    *   **Nodes**: Python functions receiving `AgentState`.
    *   **Edges**: Conditional logic (e.g., `should_continue`, `route_to_research`).
*   **Middleware**: `langgraph-checkpoint-postgres` for state persistence.

### 4.2 Frontend (`client/src/`)
*   **Routing**: App Router (`app/page.tsx`, `app/api/`).
*   **Components**:
    *   `Thread`: Main chat controller.
    *   `Artifact`: Side panel for rendering documents/reports.
    *   `ReasoningBlock`: Collapsible UI for agent thought chains.
*   **Data Fetching**:
    *   `useStream`: Custom hook wrapping `langgraph-sdk`.
    *   **Optimistic UI**: Updates chat immediately while waiting for server.

### 4.3 Crawler (`backend/src/service/crawler/`)
*   **Architecture**: Orchestrator (`NEFACCrawler`) + Strategy Pattern (`Extractors`).
*   **Modules**:
    *   `WordPressExtractor`: Paginates through WP REST API.
    *   `YouTubeExtractor`: Wraps `yt-dlp` for metadata/transcripts.
*   **Concurrency**: `ThreadPoolExecutor` for parallel downloads.
*   **Resilience**: Exponential backoff retry logic for 429/50x errors.

### 4.4 Ingestion (`backend/src/service/ingestion_service/`)
*   **Framework**: **LlamaIndex Workflows**.
*   **Pipeline**:
    1.  `Load`: Unstructured.io parsers (PDF/HTML).
    2.  `Transform`: Semantic chunking & Metadata extraction.
    3.  `Embed`: OpenAI `text-embedding-3-small`.
    4.  `Index`: Parallel writes to Qdrant, Elastic, and Neo4j.
*   **Graph RAG**: Uses `DynamicLLMPathExtractor` to extract entities based on a strict schema (`Person`, `Organization`, `LegalCase`).

## 5. Design Patterns & Best Practices

### 5.1 Patterns
*   **Supervisor-Worker**: Used in the Agent layer to manage complexity. The Supervisor plans; Workers execute.
*   **Strategy Pattern**: Used in Crawler (Extractors) and Retrieval (Search Strategies).
*   **Event-Driven**: Used in Ingestion (LlamaIndex Events) to decouple processing steps.
*   **Repository Pattern**: Implicitly used in Database interactions (abstracting Neo4j/Qdrant calls).

### 5.2 Best Practices
*   **Type Safety**: Strict Pydantic models for all Agent State and API inputs/outputs.
*   **Configuration**: 12-Factor App principles. All config via Environment Variables (`.env`).
*   **Docker Optimization**:
    *   **Multi-Stage Builds**: Frontend uses `deps` -> `builder` -> `runner`.
    *   **Layer Caching**: Backend installs dependencies before copying source code.
    *   **Non-Root Users**: Containers run as `nextjs` or restricted users where possible.
*   **Observability**: LangSmith integration for tracing agent steps and LLM calls.

## 6. Deployment & Environment

### 6.1 Docker Compose (`docker/docker-compose.yml`)
Defines the complete stack.
*   **Networking**: Internal bridge network `nefacnet`.
*   **Volumes**: Persistent storage for all databases.
*   **Healthchecks**: Ensures dependent services (Backend) wait for DBs to be healthy.

### 6.2 Environment Variables
*   **Frontend**: `NEXT_PUBLIC_API_URL` (Build time & Runtime).
*   **Backend**: `OPENAI_API_KEY`, `NEO4J_URI`, `POSTGRES_URI`.
*   **Security**: Secrets (API Keys, Passwords) are injected at runtime, never baked into images.
